P3 · Using AES safely: modes, nonces and integrity#

← P2 Block ciphers and AES · index · next: P4 Public-key cryptography →

AES encrypts exactly one 16-byte block, and always the same way. Turning it into encryption of real messages brings out two ideas that are central to homomorphic encryption. First, encryption must be randomized: encrypting the same message twice must give different ciphertexts. Second, ciphertexts can be malleable: changed in a way that changes the plaintext predictably. For ordinary encryption malleability is an attack, stopped with a MAC. For HE it is the whole point.

In this chapter you will learn to:

  • explain why encrypting block by block (ECB) leaks, and see the leak in a picture;
  • use CBC and CTR correctly, and say what an IV and a nonce must each satisfy;
  • recover a secret message when a CTR nonce is reused;
  • turn "pay $100 to Bob" into "pay $900 to Bob" without the key;
  • build encrypt-then-MAC with HMAC, and say what AES-GCM and ChaCha20-Poly1305 provide;
  • explain why HE ciphertexts must be malleable, and why that rules out this kind of integrity.

Companion script: code/primer/p3_modes.py. Run it from the homomorphic_encryption/ folder with python3 code/primer/p3_modes.py. Its output is split into numbered parts, and the text says which part shows what.

1. What a block cipher alone cannot do#

A block cipher (P2) is a keyed permutation of 16-byte blocks. Two things are missing before it can encrypt messages:

  • Length. Messages have any length. They must be cut into blocks, and the last block must be filled up.
  • Repetition. \(E_K\) is a fixed function. Encrypt the same block twice and you get the same ciphertext twice, so an eavesdropper learns when messages, or parts of messages, repeat. Think of a "yes"/"no" vote, a status field, or a file header.

A mode of operation fixes both. NIST SP 800-38A (2001) standardizes five confidentiality modes: ECB, CBC, CFB, OFB and CTR. This chapter covers ECB (what not to do), CBC and CTR. CFB and OFB are close relatives of CBC and CTR.

Padding. Modes that work on whole blocks (ECB, CBC) need padding. The usual rule, PKCS#7, appends \(n\) bytes each of value \(n\), where \(1 \le n \le 16\) is the number needed to reach a multiple of 16. "attack at dawn" has 14 bytes, so it gets 02 02. A message that already fills whole blocks gets a full extra block of sixteen 10 bytes (hex 10 = 16), so the receiver can always remove the padding unambiguously.

2. ECB and the penguin#

The obvious mode is electronic codebook (ECB): encrypt each block on its own.

     P1          P2          P3
     |           |           |
   [E_K]       [E_K]       [E_K]
     |           |           |
     C1          C2          C3          C_i = E_K(P_i)

ECB is a giant codebook: each 16-byte plaintext block always maps to the same 16-byte ciphertext block. Equal plaintext blocks give equal ciphertext blocks, anywhere in a message and across all messages under the same key. The famous illustration is the "ECB penguin": a bitmap of the Linux mascot encrypted in ECB mode is still plainly a penguin, because large areas of the same colour become large areas of the same ciphertext.

Part 2 of the script does the same with a small padlock. To keep the picture tiny, each pixel is a whole 16-byte block (in a real bitmap, one block covers a few neighbouring pixels, and uniform areas still give identical blocks). In 2023 NIST announced that the revision of SP 800-38A will restrict ECB to the few uses other NIST standards explicitly allow.

3. CBC: chaining with a random IV#

Cipher block chaining (CBC) XORs each plaintext block with the previous ciphertext block before encrypting it. The first block is XORed with an initialization vector (IV), a fresh random block for every message:

           P1              P2              P3
           |               |               |
  IV ---->(+)     +------>(+)     +------>(+)
           |      |        |      |        |
         [E_K]    |      [E_K]    |      [E_K]
           |      |        |      |        |
           C1 ----+        C2 ----+        C3
\[C_0 = \mathit{IV}, \qquad C_i = E_K(P_i \oplus C_{i-1}), \qquad P_i = D_K(C_i) \oplus C_{i-1}.\]

The IV is sent in the clear with the ciphertext. Because it is random, the same message encrypts differently every time, and equal plaintext blocks inside a message are blended with different predecessors. In the picture above (part 2 of the script), all 234 CBC blocks are different.

What CBC needs and what it costs:

  • The IV must be unpredictable (SP 800-38A, Appendix C): not secret, but impossible to guess before it is used. TLS 1.0 used the last ciphertext block of the previous record as the next IV, which an attacker could predict; the BEAST attack (2011) exploited exactly that.
  • Encryption is sequential (each block waits for the previous one); decryption can run in parallel.
  • Padding is needed, and padding errors leak. Vaudenay (2002) showed that if a receiver reveals whether the padding of a decrypted message was valid (by an error message, or just by timing), an attacker can decrypt any ciphertext byte by byte by submitting modified versions. These padding oracle attacks hit SSL/TLS, IPsec and many web frameworks. They are a first hint of §7: the attacker succeeds by modifying ciphertexts.

4. CTR: a block cipher becomes a stream cipher#

Counter mode (CTR) never encrypts the message with AES at all. It encrypts a counter, and uses the output as a pad:

   nonce||0       nonce||1       nonce||2
      |              |              |
    [E_K]          [E_K]          [E_K]
      |              |              |
      S0             S1             S2          keystream S_i = E_K(nonce || i)
      |              |              |
P0 ->(+)       P1 ->(+)       P2 ->(+)
      |              |              |
      C0             C1             C2          C_i = P_i XOR S_i

(Blocks are numbered from 0 here, to match the counter.)

This is the stream cipher of P1 §7: a short key stretched into a long pseudorandom pad, then XORed with the message, a computational one-time pad. Decryption is the same operation (XOR the same keystream again). Practical advantages: no padding (cut the last keystream block short), every block is independent (parallel, random access), and only \(E_K\) is ever used, never \(D_K\).

The counter block must never repeat under one key. Each message gets a nonce ("number used once"), and the block counter runs within the message. The toy uses an 8-byte nonce and an 8-byte block counter; AES-GCM uses a 12-byte nonce and a 4-byte counter. A nonce need not be random or secret, only unique: a message counter is fine.

Mode Per-message value Requirement Padding Parallel encryption Malleable
ECB none (deterministic) yes yes blocks can be swapped or replayed
CBC IV, 16 bytes unpredictable yes no (decryption yes) yes, with collateral damage
CTR nonce unique no yes yes, bit by bit

Note the lengths. ECB: one padded block, 16 bytes. CBC: 16-byte IV plus one block. CTR: 8-byte nonce plus exactly 14 bytes, no padding. Randomized ciphertexts are longer than the plaintext: the randomness has to travel with them (unless both sides can derive the nonce themselves, for example from a shared message counter, as TLS 1.3 does).

5. Nonce reuse: the two-time pad returns#

If two messages are encrypted under the same key and the same nonce, they use the same keystream \(S\):

\[C_1 = P_1 \oplus S, \quad C_2 = P_2 \oplus S \quad\Longrightarrow\quad C_1 \oplus C_2 = P_1 \oplus P_2.\]

The keystream cancels, exactly as in the two-time pad of P1. With one byte: \(P_1\) = 'A' = {41}, \(P_2\) = 'B' = {42}, keystream byte {9c}. Then \(C_1\) = {dd}, \(C_2\) = {de}, and \(C_1 \oplus C_2\) = {03} = 'A' ⊕ 'B', with no trace of the key. Anyone who knows or guesses \(P_1\) reads \(P_2\), and even without that, the XOR of two English texts is usually enough to recover both. Part 4 of the script:

=== 4. CTR nonce reuse = two-time pad ===
C1 xor C2 == P1 xor P2 ? True
attacker knows P1 (a public notice) and recovers P2 without the key:
   b'New vault code is 7341; tell no one!!!'

This is not hypothetical. The KRACK attacks on WPA2 Wi-Fi (Vanhoef and Piessens, 2017) tricked devices into reinstalling a key and resetting their nonces. For AES-GCM, nonce reuse is worse still: it also destroys authentication (§10).

Random nonces have their own limit. By the birthday bound, random \(b\)-bit nonces are likely to collide after about \(2^{b/2}\) messages: for 96-bit nonces, around \(2^{48}\). NIST wants the chance of any repetition to stay below \(2^{-32}\), so it limits a single AES-GCM key used with random IVs to \(2^{32}\) encryptions (SP 800-38D, §8.3).

6. Why encryption must be randomized#

Everything so far points to one rule: a secure encryption scheme cannot be deterministic.

The precise version is IND-CPA (indistinguishability under chosen-plaintext attack), defined in full in P5 §4 and summarized in 01 §2. Informally: the attacker may get encryptions of any messages it likes; it then picks two messages \(m_0, m_1\), receives the encryption of one of them, and must guess which. The scheme is secure if no efficient attacker does noticeably better than a coin flip.

  • Deterministic encryption always fails. The attacker asks for the encryption of \(m_0\) and compares it with the challenge. ECB fails this way, and so does CBC with a fixed IV.
  • CBC with a random IV and CTR with unique nonces pass, assuming AES is a pseudorandom permutation. Bellare, Desai, Jokipii and Rogaway proved this in 1997.
  • IND-CPA says nothing about tampering. CTR is IND-CPA secure and, as the next section shows, trivially malleable. Confidentiality and integrity are different goals.

7. Malleability: changing a message without reading it#

A scheme is malleable if, given a ciphertext of an unknown message \(m\), an attacker can produce a ciphertext of a related message, such as \(m \oplus \delta\) for a bit mask \(\delta\) of its choice, without the key.

CTR is malleable bit by bit. Flip bit \(j\) of the ciphertext and bit \(j\) of the decrypted plaintext flips, because the keystream cancels either way:

\[(P \oplus S \oplus \delta) \oplus S = P \oplus \delta.\]

The bit-flipping attack. A bank sends the order pay $100 to Bob encrypted in CTR mode. The attacker cannot read it, but knows the format: byte 5 (counting from 0) is the first digit of the amount. To turn '1' into '9', it needs \(\delta\) = '1' ⊕ '9':

'1'  = {31} = 0011 0001
'9'  = {39} = 0011 1001
XOR  = {08} = 0000 1000      -> flip bit 3 of ciphertext byte 5

With the numbers of part 5 of the script: ciphertext byte 5 is {d4}. The keystream byte, unknown to the attacker, is {d4} ⊕ {31} = {e5}. The attacker sends {d4} ⊕ {08} = {dc}, and the bank decrypts {dc} ⊕ {e5} = {39} = '9'.

=== 5. malleability: the CTR bit-flipping attack ===
bank sends     : 2af899a3e1f16bdce8fafcc617d4be8b6de5dbb4370708
attacker sends : 2af899a3e1f16bdce8fafcc617dcbe8b6de5dbb4370708   (one byte changed, no key used)
bank decrypts  : b'pay $900 to Bob'
and with 'Bob' -> 'Eve' as well: b'pay $900 to Eve'
CBC is malleable too (flip IV byte 5): b'pay $900 to Bob'

(The first 8 bytes of each ciphertext are the nonce.) The attacker needed no key and broke no cryptography, only knowledge of the message format, which is rarely secret.

CBC is malleable too. Flipping a bit of \(C_{i-1}\) flips the same bit of \(P_i\), at the price of turning \(P_{i-1}\) into garbage; flipping a bit of the IV flips the same bit of \(P_1\) cleanly, as the last line of part 5 shows. NIST says the same in plain words: SP 800-38D, Appendix A, calls CTR ciphertext "malleable" and gives this as the reason to combine it with authentication.

Look at the attack from the other side: \(\mathrm{Dec}(C \oplus \delta) = \mathrm{Dec}(C) \oplus \delta\). That is a homomorphism: an operation on ciphertexts that performs a known operation on the hidden plaintexts. CTR has only this one (XOR with a public constant), and here it is a weapon. Hold on to that thought for §12.

8. MACs and HMAC#

A message authentication code (MAC) is a keyed checksum. The sender computes a tag \(T = \mathrm{MAC}(K, m)\) and sends \((m, T)\); the receiver recomputes the tag with the same key and rejects the message if it differs. The security goal (unforgeability): even after seeing valid tags on many messages of its choice, an attacker cannot produce a valid tag for any new message. A MAC gives integrity and authenticity, since only key holders can make valid tags. It gives no confidentiality.

Why not just \(\mathrm{SHA\text{-}256}(K \,\|\, m)\)? SHA-256 processes its input block by block and outputs its internal state. Given \(H(K \,\|\, m)\), anyone can continue hashing and compute \(H(K \,\|\, m \,\|\, \text{pad} \,\|\, m')\) for a chosen \(m'\) without knowing \(K\): a length-extension forgery. (Here "pad" is SHA-256's own fixed length padding, which the attacker can compute from the length of \(K \,\|\, m\); it has nothing to do with a one-time pad.)

HMAC (Bellare, Canetti and Krawczyk, 1996; RFC 2104, 1997) hashes twice with two derived keys:

\[\mathrm{HMAC}(K, m) = H\big((K' \oplus \mathit{opad}) \,\|\, H((K' \oplus \mathit{ipad}) \,\|\, m)\big)\]
  • \(K'\) is the key padded with zero bytes to the hash's block size \(B\) (64 bytes for SHA-256), or first hashed if it is longer than \(B\);
  • \(\mathit{ipad}\) is the byte {36} repeated \(B\) times, \(\mathit{opad}\) the byte {5c} repeated \(B\) times.

The outer hash seals the inner one, so length extension no longer works. The script implements this formula in a few lines, and part 6 of the script checks it against Python's hmac module and the official test vector of RFC 4231:

=== 6. HMAC-SHA256 (RFC 2104) ===
stdlib hmac : 5bdcc146bf60754e6a042426089575c75a003f089d2739839dec58b964ec3843
by hand     : 5bdcc146bf60754e6a042426089575c75a003f089d2739839dec58b964ec3843
RFC 4231 test case 2: OK

One practical detail: compare tags with a constant-time function (hmac.compare_digest), not ==. An ordinary comparison stops at the first differing byte, and its timing tells an attacker how many leading bytes of a forged tag are right, so it can find the tag byte by byte.

9. Encrypt-then-MAC#

To get both confidentiality and integrity, combine an IND-CPA mode with a MAC, using two independent keys \(K_e\) and \(K_m\):

sender:    C = nonce || CTR_Ke(nonce, m)        T = HMAC(Km, C)        send C || T
receiver:  recompute HMAC(Km, C); if it differs from T: reject; else decrypt C

The tag covers the whole ciphertext including the nonce, and the receiver checks it before decrypting. A tampered ciphertext never reaches the decryption code, so there is nothing for a padding oracle or a bit-flipping attack to exploit.

There are three ways to combine the two, and they are not equally good. Bellare and Namprempre (2000) analysed them:

Composition Used historically in Verdict
Encrypt-then-MAC: MAC the ciphertext IPsec ESP secure for any IND-CPA encryption and any strongly unforgeable MAC (not even a new tag for an old message can be forged; HMAC qualifies)
MAC-then-encrypt: encrypt message and tag SSL/TLS up to 1.2 (CBC suites) not secure in general; Lucky Thirteen (2013) is a padding-oracle attack on it
Encrypt-and-MAC: MAC the plaintext, send it alongside SSH the tag can leak, e.g. whether two plaintexts are equal

The encrypt-then-MAC of part 7 of the script stops the attack of §7:

=== 7. encrypt-then-MAC stops the bit-flipping attack ===
nonce | ciphertext | tag : 6a4d5297d238f40a f5e3070ec8002e3beccba9f2dc96d0 ffd4e9e7acfb75d9...
honest message decrypts to: b'pay $100 to Bob'
forged message: authentication failed: ciphertext or tag was modified
forged message with a tag made under a guessed key: authentication failed: ciphertext or tag was modified

The attacker can still flip bits, but cannot make a valid tag for the result without \(K_m\).

10. Authenticated encryption in practice: AES-GCM and ChaCha20-Poly1305#

In practice nobody assembles encryption and MAC by hand. Modern libraries offer authenticated encryption with associated data (AEAD) as one primitive:

\[\mathrm{Enc}(K, \mathit{nonce}, \mathit{AD}, m) \to (C, T), \qquad \mathrm{Dec}(K, \mathit{nonce}, \mathit{AD}, C, T) \to m \text{ or } \bot.\]

The associated data AD (say, a packet header) is authenticated but not encrypted. Decryption either returns the message or fails; it never returns a tampered plaintext.

  • AES-GCM (Galois/Counter Mode, NIST SP 800-38D, 2007) is CTR mode plus GHASH, a keyed hash that treats the associated data and ciphertext blocks as the coefficients of a polynomial and evaluates it at a secret point \(H = E_K(0)\) in the field \(\mathrm{GF}(2^{128})\), the 128-bit cousin of the field in P2. The result, masked with one more AES output, is the tag. With AES-NI and the CPU's carry-less multiplication instruction it runs at gigabytes per second. Its weak spot is the nonce (96 bits recommended): if a nonce is ever repeated under a key, an attacker can usually recover \(H\) and then forge tags for any ciphertext (Joux, 2006; SP 800-38D, Appendix A).
  • ChaCha20-Poly1305 (RFC 8439, 2018, which replaced RFC 7539) combines Bernstein's ChaCha20 stream cipher with the Poly1305 MAC. It needs no special hardware; RFC 8439 estimates it at about three times the speed of AES on platforms without AES instructions. It also uses a 96-bit nonce, and repeating one is just as fatal.
  • TLS 1.3 (RFC 8446, 2018) allows only AEAD ciphers: AES-GCM, ChaCha20-Poly1305 and AES-CCM.
  • AES-GCM-SIV (RFC 8452, 2019) is nonce-misuse resistant: a repeated nonce only reveals whether two messages were identical, instead of breaking everything.

The rule for real code: use a vetted library's AEAD, generate keys and nonces with the operating system's random generator, and never reuse a nonce. The modes in this chapter's script are for understanding only.

12. How this connects to homomorphic encryption#

  • HE encryption is randomized, for the same reason as CBC and CTR. Every HE scheme in these notes is IND-CPA secure, so it cannot be deterministic. In LWE (P7) each encryption draws a fresh random mask a and fresh noise e, which play the role of the IV or nonce: encrypting 0 twice gives two completely different ciphertexts. HE ciphertexts are also much larger than their plaintexts, partly for the same reason: the random mask travels with the ciphertext.
  • Malleability is the feature. This chapter treated malleability as an attack: the attacker turned \(\mathrm{Enc}(m)\) into \(\mathrm{Enc}(m \oplus \delta)\). Homomorphic encryption is malleability made rich and controllable: anyone holding \(\mathrm{Enc}(a)\) and \(\mathrm{Enc}(b)\) can make \(\mathrm{Enc}(a + b)\) and \(\mathrm{Enc}(a \cdot b)\), and from those any circuit (P6). CTR's "flip a ciphertext bit, flip a plaintext bit" is a tiny homomorphism; HE extends it to arbitrary computation.
  • So HE results cannot carry a MAC. A MAC or AEAD rejects every ciphertext that the key holder did not produce. But producing new ciphertexts is exactly the server's job, and the server has no MAC key (if it had one, it could forge anything). The integrity check would reject every honest result. HE therefore has no built-in integrity: a malicious server can evaluate the wrong function or return an encryption of garbage, and decryption will not notice. See 01 §5. Remedies come from outside HE (05 §11). The umbrella term is verifiable computation: ways to check that a computation was done correctly without redoing it. The main tools:
    • a zero-knowledge (ZK) proof: a proof that the computation was done correctly that reveals nothing else (succinct versions, SNARKs and STARKs, are cheap to check);
    • redundancy: several independent servers compute the same result, and the client accepts only if they agree;
    • a trusted execution environment (TEE): a hardware enclave that computes on plaintext in protected memory; running the HE evaluator inside one adds a second line of defence;
    • secure multi-party computation (MPC): several parties compute jointly on secret shares of the data; versions secure against cheating parties detect a wrong result unless too many of them collude.
  • And HE can never be IND-CCA2, the stronger notion in which the attacker may also ask for decryptions: it would maul the challenge and ask for the decryption of the result. P5 §7 gives the argument.
  • AEAD still has a place around HE. HE ciphertexts travel over TLS like any other data, and the transport layer's AEAD protects them in transit. What no MAC can cover is the computation itself.

13. Check yourself#

  1. Give a concrete IND-CPA attack on ECB. Does it need more than one block?
    Show answer

    Choose \(m_0\) = two equal blocks \(X \| X\) and \(m_1\) = two different blocks \(X \| Y\). Under ECB the challenge ciphertext has two equal blocks exactly when it encrypts \(m_0\). With one-block messages it is even simpler: ask the encryption oracle for \(\mathrm{Enc}(m_0)\) and compare it with the challenge. Any deterministic scheme falls to this.

  2. CBC needs an unpredictable IV, CTR only a unique nonce. Why the difference? What goes wrong in each mode when the requirement is violated?
    Show answer

    In CBC the IV is XORed into the first plaintext block before AES. Suppose an earlier block was encrypted as \(C_j = E_K(P_j \oplus C_{j-1})\) and the attacker wants to test a guess \(G\) for \(P_j\). If it can predict the next IV, it submits \(P_1 = \mathit{IV} \oplus C_{j-1} \oplus G\), which is encrypted as \(E_K(C_{j-1} \oplus G)\): equal to \(C_j\) exactly when the guess is right. That is what BEAST did. In CTR the nonce never mixes with the plaintext; it only selects the keystream. Predicting it does not help, but repeating it reuses the keystream, a two-time pad.

  3. Two messages were encrypted with CTR under the same key and nonce. You know the first one is HELLO. What do you learn about the second, and what do you not learn?
    Show answer

    XOR the two ciphertexts and then XOR with HELLO: you get the first 5 bytes of the second message exactly. You learn nothing about bytes beyond the known length of the first message, and nothing about the key, which remains safe for messages with other nonces.

  4. A CTR ciphertext encrypts pay $100 to Bob. Which ciphertext byte do you change, and by XOR with which value, to make it pay $500 to Bob?
    Show answer

    Byte 5 (counting from 0, after the nonce): '1' = {31} and '5' = {35}, so XOR that ciphertext byte with {31} ⊕ {35} = {04}.

  5. Why encrypt-then-MAC rather than MAC-then-encrypt? Why two separate keys?
    Show answer

    Encrypt-then-MAC checks integrity before any decryption happens, so tampered ciphertexts are rejected without ever touching padding checks or decryption code that might leak (Lucky Thirteen attacked MAC-then-encrypt this way), and Bellare and Namprempre proved it secure generically. Separate keys avoid unwanted interaction between two algorithms that were each analysed on their own with an independent key.

  6. Why can't a server that computes on HE ciphertexts return results protected by AES-GCM-style authentication? What does that mean for a client that does not trust the server?
    Show answer

    Authentication rejects any ciphertext that the key holder did not create, but the server's whole job is to create new ciphertexts by computing on old ones; the client never saw them, and giving the server the MAC key would let it forge anything. So HE outputs carry no integrity guarantee. A client that does not trust the server needs extra machinery: verifiable computation (proofs of correct evaluation), redundancy across independent servers, or trusted hardware.

14. Key terms#

Term Meaning
Mode of operation Rule for using a block cipher on messages of any length
PKCS#7 padding Append \(n\) bytes of value \(n\) to reach a whole number of blocks
ECB Encrypt each block independently; deterministic, leaks equal blocks
CBC XOR each block with the previous ciphertext block before encrypting; needs a random IV
Initialization vector (IV) Per-message random block for CBC; public but unpredictable
CTR Encrypt a counter to make a keystream and XOR it with the message
Nonce Per-message value that must never repeat under a key; need not be random
Keystream The pad \(E_K(\mathit{nonce} \Vert i)\) that CTR XORs with the message
Two-time pad Reusing a keystream: \(C_1 \oplus C_2 = P_1 \oplus P_2\)
Randomized encryption Encrypting the same message twice gives different ciphertexts; required for IND-CPA
Padding oracle Leak of whether decrypted padding was valid; enough to decrypt CBC ciphertexts
Malleability Ability to turn a ciphertext of \(m\) into one of a related message without the key
Bit-flipping attack Exploiting CTR or CBC malleability to change chosen plaintext bits
MAC / tag Keyed checksum that only key holders can compute; gives integrity and authenticity
Length extension Forging \(H(K \Vert m \Vert \text{pad} \Vert m')\) from \(H(K \Vert m)\); breaks naive hash MACs
HMAC Hash-based MAC, \(H((K' \oplus \mathit{opad}) \Vert H((K' \oplus \mathit{ipad}) \Vert m))\) (RFC 2104)
Encrypt-then-MAC Encrypt, then MAC the ciphertext; check the tag before decrypting
AEAD Authenticated encryption with associated data: one primitive for secrecy and integrity
AES-GCM AEAD from CTR mode plus the GHASH polynomial MAC (SP 800-38D)
ChaCha20-Poly1305 AEAD from the ChaCha20 stream cipher and the Poly1305 MAC (RFC 8439)
Nonce-misuse resistance Repeating a nonce leaks only message equality (e.g. AES-GCM-SIV)
Verifiable computation Checking that a computation was done correctly without redoing it
Zero-knowledge (ZK) proof Proof that a computation was done correctly that reveals nothing else
TEE Trusted execution environment: a hardware enclave computing on plaintext in protected memory
MPC Secure multi-party computation: several parties compute jointly on secret shares
